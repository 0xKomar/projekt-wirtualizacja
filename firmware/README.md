# ESP32 firmware: synthetic noise measurements over Wi-Fi

This PlatformIO/Arduino sketch runs on an ESP32, generates ten synthetic
one-second sample values on the board (no microphone or soldering required),
aggregates them, and sends each window to `POST /api/readings` over Wi-Fi with
`X-Device-Key`. It is actual network traffic from the ESP32; the measurement
values are simulated in firmware.

The default profile emits four loud windows (samples centered near 75 units),
then normal windows (near 55). The backend should create a `noise_threshold`
event after the sustained windows when the device has an enabled alert rule
configured for 70 units over 10 seconds. The event is generated by the backend,
not by the ESP32.

## Acoustic-threshold research

Published thresholds are tied to measurement methods and exposure periods, not
an arbitrary ten-second average. NIOSH's occupational recommendation is 85 dBA
as an 8-hour time-weighted average, with exposure duration halved for every
3 dBA increase. WHO's European night-noise guideline uses annual-average
outdoor `Lnight` (40 dB target; 55 dB interim target). These values are not
interchangeable with this project's uncalibrated sample values. Therefore the
70-unit / 10-second rule is a **demo trigger only**, not a health, workplace, or
regulatory threshold. Do not interpret it as dB SPL or dBA. Source publications:
NIOSH, *Criteria for a Recommended Standard: Occupational Noise Exposure*
(publication 98-126); WHO Regional Office for Europe, *Night Noise Guidelines
for Europe* (2009).

## Provision the backend once

Create a location and device using the project's API (`POST /api/locations`,
then `POST /api/devices` with the returned `location_id`). The device creation
response provides a one-time device key; keep it locally. Create a rule for that
device using `POST /api/alert-rules`, for example:

```json
{
  "name": "ESP32 synthetic demo",
  "device_id": 123,
  "threshold_db": 70,
  "min_duration_seconds": 10,
  "enabled": true
}
```

Replace `123` with the created device ID. The rule is just for demonstrating the
alert path; choose calibrated thresholds only after the measurement method and
exposure metric have been defined.

## Configure and upload

The default PlatformIO target is the generic `esp32dev` board. An optional
`esp32s3` profile targets `esp32-s3-devkitc-1`. Check the actual board model
before uploading; if it is another variant (including a different ESP32-S3
board), select its correct PlatformIO board ID. Hardware model is not assumed
here.

From `firmware/`, provide these environment variables in your local shell or a
private environment file (never commit that file):

| Variable | Value |
| --- | --- |
| `WIFI_SSID` | Wi-Fi network name |
| `WIFI_PASSWORD` | Wi-Fi password |
| `BACKEND_URL` | Backend base URL; use an `https://` URL with the default profiles |
| `DEVICE_KEY` | One-time key returned when creating the device |

If you keep the values in `firmware/.env.local`, make it private and source it
before running PlatformIO:

```sh
chmod 600 .env.local
set -a
. ./.env.local
set +a
```

Then run:

```sh
pio run -e esp32dev
pio run -e esp32dev -t upload
pio device monitor -b 115200
```

For the supported ESP32-S3 DevKitC-1 profile, use `-e esp32s3` for both build
and upload commands. Do not flash until the board model is confirmed. The
default `esp32dev` and `esp32s3` profiles require HTTPS and verify certificates
against the ESP32 platform's built-in CA bundle.

For a local backend that only serves HTTP, explicitly select `esp32dev-http` or
`esp32s3-http` for build and upload. These profiles require an RFC1918 private
IPv4 address literal and cannot be used with public IPs or hostnames. They send
the device key in cleartext; use them only on a trusted, isolated LAN. Plain
HTTP is rejected by the default profiles at compile time.

The key is compiled into the firmware image; protect the image and local config
like credentials. On HTTP 401 the ESP stops sending rather than creating a new
device. Network/5xx failures keep up to three readings in RAM and retry; if the
buffer fills, the oldest unsent window is discarded.

Native tests cover sample generation, aggregation, sampling cadence, and the
transport-security policy:

```sh
g++ -std=c++17 -Wall -Wextra -Werror -Iinclude \
  test/native/test_simulation.cpp -o /tmp/test_simulation
/tmp/test_simulation
```

A successful native test does not verify PlatformIO compilation, Wi-Fi, board
upload, the live server, or physical ESP behavior. Those require the board,
credentials, and deployed API.
